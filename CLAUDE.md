# Roomie (IS 401 roommate app)

## Stack and commands
- Frontend: static HTML/CSS/JS today (the Lovable-style mockup in the repo root), moving to Vite. Backend: Vercel serverless functions in `api/` (TypeScript, Web-standard `GET/POST/PATCH` exports). Data: Neon Postgres via Drizzle (`api/_lib/schema.ts` is GENERATED by `npm run db:pull`; never edit it). Sign-in: Neon Auth.
- `npm run dev:api` local API on :3001 (also proxies `/api/auth/*` to Neon Auth), `npm run dev` Vite on :5173 (proxies `/api` to it). `public/phone.html` shows the app in an iPhone frame; `public/mockup/` is the old plain-file mockup.
- `npm test` unit tests (money math, balances, route guards) | `npm run test:security` live API tests (auth, access, money rules; ~150 checks) | `npm run test:seed` joins the seed household as a 5th member | `npm run test:preview -- <url>` sign-in on a deployed domain | `npm run test:cleanup` removes any leftover `roomie-test-*` rows | `npm run typecheck`
- `npm run db:pull` refresh Drizzle types from the live database after a migration | `npm run db:seed` / `npm run db:unseed` demo data (join code MAPLE412; users `maple.*@example.com`)
- Deploy: `vercel deploy --yes` then `vercel alias set <url> roomie-is401-preview.vercel.app` (that exact origin is trusted in Neon Auth). Preview env vars: `DATABASE_URL`, `NEON_AUTH_URL`.
- Env lives in `.env.local` (git-ignored, see `.env.example`). It points at the Neon **dev** branch.
- Git: `main` is connected to Vercel, so a push to `main` is a **production** deploy (public). Work on feature branches (a push to a branch deploys a protected preview that uses dev). Merge to `main` only when Michael says to.

## Which Neon branch is used where
- **dev**: local dev, all test suites (`test`, `test:security`, `test:seed`, `test:preview`, `test:cleanup`), the UI fixture, `db:pull`, and **Vercel Preview** deploys. `.env.local`.
- **main**: production and the demo only (Vercel Production env). `.env.production.local`. Never source it, read from it, or write to it unless Michael explicitly asks for a production action; use `db:migrate:prod` / `db:seed:prod` for those.
- The test scripts refuse to run against main (`scripts/lib/db-guard.ts`). Do not weaken or bypass that guard.
- Migrations go to dev first (`npm run db:migrate -- <file>`), pass all suites, get Michael's review, then `db:migrate:prod`. Details in `db/README.md`.

## Database

### Schema
- `db/schema.sql` is the source of truth. Never edit tables by hand; any change is a new numbered file in `db/migrations/` that Michael reviews before it runs.
- `updated_at` is set by a database trigger. Don't set it in app code.

### Access
- Every query must be scoped to a household the current user belongs to: a `household_member` row with `left_date IS NULL`. We are not using row-level security, so this is the only thing keeping households' data apart.
- A roommate who moved out (`left_date` set) keeps their history visible but gets no new chores, shares, tags, or notifications.
- Only the creator can edit chores, events, and wishlist items (`created_by_user_id`).

### Money
- Balances are always calculated, never stored. For each pair of roommates: sum of their unsettled-or-settled shares on expenses the other person paid for, minus confirmed payments between them, netted in both directions. Only `payment.status = 'confirmed'` counts.
- The buyer's own share (`expense_share.user_id = expense.paid_by_user_id`) is never owed and never appears in balances.
- A share is "paid back" only when `settled_by_payment_id` points to a payment with status `confirmed`. If that payment is `sent` show it as pending; if `disputed`, show disputed. Never add an `is_paid` flag.
- When someone pays back specific items, create the payment and set `settled_by_payment_id` on those shares in the same transaction. The payment amount must equal the sum of the shares it settles.
- Store money as NUMERIC and do math in cents or a decimal type, never floats. When splitting, give leftover cents to the first shares so shares sum exactly to `total_amount`.

### Chores, calendar, notifications
- `chore` rows are the rule; `chore_assignment` rows are generated occurrences, created by a scheduled job (Vercel Cron) a few weeks ahead. Build `due_at` from the chore's day/time in `household.timezone`. The unique `(chore_id, due_at)` constraint makes the job safe to re-run.
- Respect `last_reminded_at` so reminders don't spam.
- Accept/decline lives on the source record (`chore_swap_request.status`, `event_tag.response`, `payment.status`). `notification` only points at it via `source_type` + `source_id`.
- When an action should notify roommates, insert the notification rows in the same transaction as the action.
- Show all times in the household's timezone.

### Secrets
- Never hardcode credentials.

## Security (there is no row-level security, so these are the only walls)
- The Neon Data API stays OFF. `authenticated` and `anonymous` have zero privileges on every public table and zero default privileges on future ones. Never `GRANT` anything to them. If a migration creates tables or functions, re-check this with `npm run test:security`.
- Only `api/` functions touch the database, using `DATABASE_URL` (the table-owner role `neondb_owner`) on the server. Never put a database URL or secret in frontend code, `src/`, or any `VITE_` variable.
- Every route is wrapped in `withUser` (needs sign-in), `withHousehold` (also proves the caller is an active member via `requireActiveMember`), `withCron`, or `withSignedLink` for the signed unsubscribe capability. Do not write a household query anywhere else without the appropriate guard. A guard test fails the build if a route is not wrapped.
- Who is acting comes only from the verified token. The household id comes only from the URL path. Never read a user id, role, or household id from the request body or query string.
- Non-members get 404, never 403, so household ids cannot be probed. Only the creator can edit (`assertCreator`). New chores, shares, tags and notifications go through `assertActiveMembers` so a roommate who moved out is never targeted.
- Never link a sign-in to an existing `users` row by email (anyone can register any email). `users` rows are created on first sign-in from the token's `sub`, stored in `users.auth_provider_id`.
- Sign-in goes through our own domain (`/api/auth/*` rewritten to the `api/auth-proxy.ts` function, NOT a plain rewrite to Neon: Vercel forwards the wrong Host and Neon answers INVALID_HOSTNAME) so the cookie is first-party and Safari keeps it. The proxy forwards only `neon-auth.*` cookies (newest per name), never any other cookie, and rewrites Neon's `SameSite=None; Partitioned` cookie to `SameSite=Lax`. The API wants the 15-minute JWT; `src/auth-client.js` refreshes it a minute before expiry and retries once on 401.
- Vercel file routing only matches ONE path segment per `[param]`/`[...rest]`, so all of `/api/*` goes through `vercel.json` rewrites into `api/router.ts` (one route table in `api/_lib/routes.ts`) and `api/auth-proxy.ts`. Add routes to the table, not as new files in `api/` (Hobby plan: max 12 functions).
- Browser code never imports from `api/` (Vite proxies that path to the server in dev). Shared pure code lives in `shared/` (money.ts, balances.ts).
- After every migration and before finishing any slice, run `npm run test:security`. These tests create real throwaway `roomie-test-*` accounts and delete them (and sweep leftovers) on every run. They must leave zero `roomie-test-*` rows behind.
- Before real launch: add the production domain (exact origin, no wildcard on a shared host like vercel.app) to Neon Auth trusted origins, and add rate limiting on join-code attempts. Signup email verification is intentionally not required; notification destinations have their own confirmation flow.


## Money (slice a: Expense tracker, built)
- Pure logic in `shared/balances.ts` (calculated balances, share status) and `shared/money.ts` (cents, exact splits). Server rules in `api/_lib/finance.ts`; handlers in `api/_lib/handlers/`.
- `paid_by` is always the caller. A payment's amount is computed on the server from the shares it settles, never read from the request. Only the payee can confirm or dispute (sent -> confirmed|disputed, disputed -> confirmed, confirmed is final). A buyer can delete an expense only while no share has a payment on it.
- Not built yet: editing an expense, custom (unequal) splits, receipt photos, recurring bills/rent. Notification rows are created by every action; the notifications screen is slice (d).

## Chores (slice b, built)
- Rules vs occurrences: a `chore` row is the rule; `chore_assignment` rows are generated occurrences. A fixed assignee is a rotation of one (`chore_rotation`); one-time chores get their single assignment at creation. Pure scheduling lives in `shared/chore-dates.ts` (weekly, monthly with month-end clamping, next-in-rotation); server rules in `api/_lib/chores.ts`; handlers in `api/_lib/handlers/`.
- `due_at` is built in Postgres as `(date + time) AT TIME ZONE household.timezone`, so 6 PM stays 6 PM across daylight saving. Generation (`generateForChore`) runs when a chore is created and daily from Vercel Cron (`/api/cron/chores`, `vercel.json`, protected by `CRON_SECRET`; fails closed with 503 if unset). It only creates missing occurrences and only assigns CURRENT roommates, continuing the rotation from the previous assignee.
- Reminders: the same cron sends one reminder per occurrence due in the next 24h and sets `last_reminded_at`; a roommate's manual nudge shares that throttle (429 within 12h). Nobody who moved out is reminded, assigned, or asked.
- Swap and skip (`chore_swap_request`): a swap goes to the one roommate who owns the target occurrence. v3 has no recipient column, so a skip goes to every other current roommate and the FIRST to accept takes the chore ("Not me" is recorded nowhere except marking that person's own notification read). Accepting a swap exchanges both assignees in one transaction. Open requests are auto-closed when their chore is marked done. A request can only be withdrawn by the person who asked.
- Only the assignee marks a chore done or undoes it. The owner edits or deletes it (schedule changes mean delete and re-add); ownership of a one-time chore follows its assignee after an accepted swap or cover request, while recurring-rule ownership never transfers. Status (done / overdue / upcoming) is derived, never stored.
- Production needs `CRON_SECRET` in Vercel Production env (set). Crons never run on previews.

## Calendar and board (slice c, built)
- Rules in `api/_lib/calendar.ts`; handlers `events`, `event-one`, `event-respond`, `board`, `board-one` (registered in `routes.ts`). Page: `src/pages/calendar.js` (event-only list and month views, board beside it, polls every 15s while open and nobody is typing). Chores stay on their own page; Home is the combined Calendar / Upcoming list view.
- Events: only the creator edits or deletes (`assertCreator`). Start and end are built in Postgres from date + time in `household.timezone`. Tagged roommates must be current (`assertActiveMembers`); the creator is never tagged. Every newly selected approver receives `event_tag.response = 'pending'`, for every category. All selected approvals are required to confirm a plan; any decline shows Changes requested. Existing informational tags with null responses stay informational. Only the tagged person answers (`POST .../events/:id/respond`), always for themselves, and the creator is notified. Editing replaces the approver list; changing the plan resets current approvers to pending and notifies them again, while unchanged saves preserve votes. Pending or declined plans do not receive confirmed-event reminders.
- Board: a note is a `bulletin_message`; a reply has `parent_message_id` (one level only). Only the sender edits, pins or deletes; deleting a note removes its replies and notifications. A reply notifies the note's author. A note can link one event of the same household.
- Event reminders use the daily cron. Event creation can also attach an `.ics` file to opted-in emails. Not built: calendar import, repeating events, true push or websocket realtime (polling instead).

## Personal activity (notifications)
- The bell opens a compact Activity panel on the current page, with the caller’s personal updates, unread dots/count, and Mark all read. No duplicate approval, swap, or payment response buttons are shown in the panel.
- Selecting an update marks it read, switches to its active household, and opens the relevant feature. Event and chore details open after page data loads; announcements scroll to their thread; payment updates focus their finance record without confirming anything. Expense and wish-list details open when available. Legacy `#/notifications` links open Home with the activity panel.
- Approving/declining an event marks the caller’s original invitation read in the response transaction, including idempotent responses. Finalized cover/swaps clear their old invitations before sending the requester a new outcome update; personal cover declines clear only that viewer’s invitation. Read or already-resolved request questions are omitted from the inbox and badge counts, including legacy answered notifications. Fresh reapproval requests and separate outcome messages remain.
- The existing authenticated notifications endpoints and 30-second count polling remain. The household board remains the shared announcements/request workspace. No database migration or notification deletion.
- Not built: phone push notifications, email, per-type mute settings.

## Onboarding wizard
- New memberships have `household_member.onboarded_at = NULL`; existing memberships were backfilled during migration `0003`. `GET /me` returns `onboardedAt`, and `src/main.js` keeps the current membership in the six-step wizard until `POST /households/:id/onboarding/complete` succeeds.
- The wizard covers profile, join/create, editable starter setup, owner invite, per-household email choices, and a quick tour. Members joining an already configured household get a read-only welcome brief instead of setup suggestions. Progress is kept in `sessionStorage`.
- `POST /households/:id/onboarding/suggest` is guarded by `withHousehold`. It sends only capped answers, current first names, and the household timezone to the configured model, uses a forced tool schema, then projects the response through `validateOnboardingDraft`. User ids and extra model fields are ignored. AI never writes: confirmation uses the existing chore, board, and wishlist routes and can retry remaining items.
- AI is optional. `ONBOARDING_AI_ENABLED=1` plus either direct Anthropic or `OPENROUTER_API_KEY` + `OPENROUTER_MODEL` enables it. Invalid output, timeouts, disabled flags, and hourly limits use `shared/onboarding-templates.ts`. Limits are 3 suggestions per person/household/hour in `ai_usage`.
- Email preference rows are managed at `GET/PUT /households/:id/notification-settings`; missing rows mean off.

## Event email
- Creating an event queues current, opted-in roommates with a separately verified notification channel in `email_outbox` inside the event transaction. The creator is excluded; a tagged approver uses `approval_request`, otherwise hosting and other events use their matching kind. “Notify roommates” defaults off, and `EVENT_EMAIL_ENABLED=1` is the whole-app kill switch.
- `api/_lib/event-email.ts` sends through Resend after commit using Vercel `waitUntil`; the daily cron retries pending/failed rows up to three attempts for two days. It rechecks membership, verification, preference, and start time before every send. Deleting an event skips unsent rows. A 20-email household/day queue cap and outbox uniqueness limit abuse and duplicates.
- Emails use a deterministic database-backed template, optional AI intro behind `EVENT_EMAIL_AI_ENABLED`, event deep link, `.ics` attachment, and Resend idempotency key. Signed 60-day links support confirmation and one-click unsubscribe without sign-in; tokens contain only user id, household id, and kind.
- Notification-channel confirmation is separate from sign-in. Raw confirmation tokens are emailed once, stored only as SHA-256 hashes, expire after about 24 hours, and are consumed atomically. Destination hashes use HMAC-SHA-256 with `NOTIFICATION_HASH_SECRET`; changing the destination clears verification, and confirmation succeeds only when its hash still matches the current normalized address. Sends are limited per user and per address.
- Real delivery stays OFF until a sending domain is verified in Resend and Preview has server-only `RESEND_API_KEY`, `EMAIL_FROM`, `EMAIL_LINK_SECRET`, `NOTIFICATION_HASH_SECRET`, `APP_ORIGIN`, and `EVENT_EMAIL_ENABLED=1`. Set Production only after Preview proves confirmation, delivery, and unsubscribe. Sending an AI intro also requires team approval for event/household text leaving Roomie.

## Home (slice e, built)
- `src/pages/home.js` is the landing page: Shared household schedule heading with a short overview description, one full-width schedule combining everyone’s events and chore occurrences, Calendar view / List view dropdown, and a compact finance overview. Both views use `scheduleItems` in `shared/home-schedule.ts` and household-local dates. Month navigation and day details are available in Calendar, without a Today shortcut; List view shows only the selected month, grouped chronologically by day. Both views share month navigation and keep the selected month when switching formats. Card customization and separate My chores are removed; only the display format is remembered per user and household. It composes existing endpoints with no new data route.
- Profile Save is available even when unchanged, disabled only during submission; success rebuilds the form from the canonical server response, confirms the save inline, and updates the header avatar.
- **The AI line is behind a flag and OFF by default** (M-09). `GET /households/:id/home-summary` returns `{ enabled: false }` unless the server has `HOME_AI_ENABLED=1` and either direct Anthropic credentials or an OpenRouter key and model. The snapshot is built server-side in `api/_lib/home.ts` from the database, for ONE household the caller belongs to (never from the request), and holds first names, event and chore names, balances and up to 3 board notes. No emails, phone numbers or ids. Roommate-written text is flattened, capped and sent as data inside `<snapshot>` tags (`buildAiPrompt`), the model's reply is cut to one plain paragraph (`cleanAiText`) and shown with `textContent`. Limits: 6 calls per person, household and feature per hour (recorded in `ai_usage`), one call per sign-in (sessionStorage), 15s timeout, a failure just hides the line. Turning it on sends household text to a third party, so tell the team first.
- DB pool: `api/_lib/db.ts` now handles `error` on the pool and on checked-out clients (a dropped Neon connection used to crash the process with an uncaught exception).

## Weekly recap (Home)
- A fixed "Your week" card above the Home dashboard (not a draggable widget). `GET /households/:id/weekly-recap` (`withHousehold`, `api/_lib/handlers/weekly-recap.ts`) returns `{ enabled: false }` unless `RECAP_AI_ENABLED=1` and an AI key is set (OpenRouter: `OPENROUTER_API_KEY` + `OPENROUTER_MODEL`, optional `RECAP_AI_MODEL`). It reuses the Home snapshot (first names, item text, no emails or ids) plus the caller's last seven days, via `buildRecapPrompt`. Output is hard-capped to 2 sentences and 45 words by `capSentences`, whatever the model returns.
- "Every day" is a per-browser cache (`roomie.home.recap.<user>.<household>`, household-local date); the Refresh recap button bypasses it. Limit is 6 calls per person, household and feature per hour (`ai_usage`, feature `recap`). No migration. Turning it on sends household text to a third party, so tell the team first.
