# Roomie (IS 401 roommate app)

## Stack and commands
- Frontend: static HTML/CSS/JS today (the Lovable-style mockup in the repo root), moving to Vite. Backend: Vercel serverless functions in `api/` (TypeScript, Web-standard `GET/POST/PATCH` exports). Data: Neon Postgres via Drizzle (`api/_lib/schema.ts` is GENERATED by `npm run db:pull`; never edit it). Sign-in: Neon Auth.
- `npm run dev:api` local API on :3001 (also proxies `/api/auth/*` to Neon Auth), `npm run dev` Vite on :5173 (proxies `/api` to it). `public/phone.html` shows the app in an iPhone frame; `public/mockup/` is the old plain-file mockup.
- `npm test` unit tests (money math, balances, route guards) | `npm run test:security` live API tests (auth, access, money rules; ~150 checks) | `npm run test:seed` joins the seed household as a 5th member | `npm run test:preview -- <url>` sign-in on a deployed domain | `npm run test:cleanup` removes any leftover `roomie-test-*` rows | `npm run typecheck`
- `npm run db:pull` refresh Drizzle types from the live database after a migration | `npm run db:seed` / `npm run db:unseed` demo data (join code MAPLE412; users `maple.*@example.com`)
- Deploy: `vercel deploy --yes` then `vercel alias set <url> roomie-is401-preview.vercel.app` (that exact origin is trusted in Neon Auth). Preview env vars: `DATABASE_URL`, `NEON_AUTH_URL`.
- Env lives in `.env.local` (git-ignored, see `.env.example`). It points at the Neon **dev** branch.
- Git: `main` is connected to Vercel, so a push to `main` is a **production** deploy (public). Work on feature branches (a push to a branch deploys a protected preview that uses dev). Merge to `main` only when Michael says to.

## Which Neon branch is used where
- **dev**: local dev, all test suites (`test`, `test:security`, `test:seed`, `test:preview`, `test:cleanup`), the UI fixture, `db:pull`, and **Vercel Preview** deploys. `.env.local`.
- **main**: production and the demo only (Vercel Production env). `.env.production.local`. Never source it, read from it, or write to it unless Michael explicitly asks for a production action; use `db:migrate:prod` / `db:seed:prod` for those.
- The test scripts refuse to run against main (`scripts/lib/db-guard.ts`). Do not weaken or bypass that guard.
- Migrations go to dev first (`npm run db:migrate -- <file>`), pass all suites, get Michael's review, then `db:migrate:prod`. Details in `db/README.md`.

## Database

### Schema
- `db/schema.sql` is the source of truth. Never edit tables by hand; any change is a new numbered file in `db/migrations/` that Michael reviews before it runs.
- `updated_at` is set by a database trigger. Don't set it in app code.

### Access
- Every query must be scoped to a household the current user belongs to: a `household_member` row with `left_date IS NULL`. We are not using row-level security, so this is the only thing keeping households' data apart.
- A roommate who moved out (`left_date` set) keeps their history visible but gets no new chores, shares, tags, or notifications.
- Only the creator can edit chores, events, and wishlist items (`created_by_user_id`).

### Money
- Balances are always calculated, never stored. For each pair of roommates: sum of their unsettled-or-settled shares on expenses the other person paid for, minus confirmed payments between them, netted in both directions. Only `payment.status = 'confirmed'` counts.
- The buyer's own share (`expense_share.user_id = expense.paid_by_user_id`) is never owed and never appears in balances.
- A share is "paid back" only when `settled_by_payment_id` points to a payment with status `confirmed`. If that payment is `sent` show it as pending; if `disputed`, show disputed. Never add an `is_paid` flag.
- When someone pays back specific items, create the payment and set `settled_by_payment_id` on those shares in the same transaction. The payment amount must equal the sum of the shares it settles.
- Store money as NUMERIC and do math in cents or a decimal type, never floats. When splitting, give leftover cents to the first shares so shares sum exactly to `total_amount`.

### Chores, calendar, notifications
- `chore` rows are the rule; `chore_assignment` rows are generated occurrences, created by a scheduled job (Vercel Cron) a few weeks ahead. Build `due_at` from the chore's day/time in `household.timezone`. The unique `(chore_id, due_at)` constraint makes the job safe to re-run.
- Respect `last_reminded_at` so reminders don't spam.
- Accept/decline lives on the source record (`chore_swap_request.status`, `event_tag.response`, `payment.status`). `notification` only points at it via `source_type` + `source_id`.
- When an action should notify roommates, insert the notification rows in the same transaction as the action.
- Show all times in the household's timezone.

### Secrets
- Never hardcode credentials.

## Security (there is no row-level security, so these are the only walls)
- The Neon Data API stays OFF. `authenticated` and `anonymous` have zero privileges on every public table and zero default privileges on future ones. Never `GRANT` anything to them. If a migration creates tables or functions, re-check this with `npm run test:security`.
- Only `api/` functions touch the database, using `DATABASE_URL` (the table-owner role `neondb_owner`) on the server. Never put a database URL or secret in frontend code, `src/`, or any `VITE_` variable.
- Every route is wrapped in `withUser` (needs sign-in) or `withHousehold` (also proves the caller is an active member via `requireActiveMember`, the single membership helper in `api/_lib/household.ts`). Do not write a household query anywhere else without calling it. A guard test fails the build if a route is not wrapped.
- Who is acting comes only from the verified token. The household id comes only from the URL path. Never read a user id, role, or household id from the request body or query string.
- Non-members get 404, never 403, so household ids cannot be probed. Only the creator can edit (`assertCreator`). New chores, shares, tags and notifications go through `assertActiveMembers` so a roommate who moved out is never targeted.
- Never link a sign-in to an existing `users` row by email (anyone can register any email). `users` rows are created on first sign-in from the token's `sub`, stored in `users.auth_provider_id`.
- Sign-in goes through our own domain (`/api/auth/*` rewritten to the `api/auth-proxy.ts` function, NOT a plain rewrite to Neon: Vercel forwards the wrong Host and Neon answers INVALID_HOSTNAME) so the cookie is first-party and Safari keeps it. The proxy forwards only `neon-auth.*` cookies (newest per name), never any other cookie, and rewrites Neon's `SameSite=None; Partitioned` cookie to `SameSite=Lax`. The API wants the 15-minute JWT; `src/auth-client.js` refreshes it a minute before expiry and retries once on 401.
- Vercel file routing only matches ONE path segment per `[param]`/`[...rest]`, so all of `/api/*` goes through `vercel.json` rewrites into `api/router.ts` (one route table in `api/_lib/routes.ts`) and `api/auth-proxy.ts`. Add routes to the table, not as new files in `api/` (Hobby plan: max 12 functions).
- Browser code never imports from `api/` (Vite proxies that path to the server in dev). Shared pure code lives in `shared/` (money.ts, balances.ts).
- After every migration and before finishing any slice, run `npm run test:security`. These tests create real throwaway `roomie-test-*` accounts and delete them (and sweep leftovers) on every run. They must leave zero `roomie-test-*` rows behind.
- Before real launch: turn on email verification in Neon Auth, add the production domain (exact origin, no wildcard on a shared host like vercel.app) to Neon Auth trusted origins, and add rate limiting on join-code attempts.


## Money (slice a: Expense tracker, built)
- Pure logic in `shared/balances.ts` (calculated balances, share status) and `shared/money.ts` (cents, exact splits). Server rules in `api/_lib/finance.ts`; handlers in `api/_lib/handlers/`.
- `paid_by` is always the caller. A payment's amount is computed on the server from the shares it settles, never read from the request. Only the payee can confirm or dispute (sent -> confirmed|disputed, disputed -> confirmed, confirmed is final). A buyer can delete an expense only while no share has a payment on it.
- Not built yet: editing an expense, custom (unequal) splits, receipt photos, recurring bills/rent. Notification rows are created by every action; the notifications screen is slice (d).
